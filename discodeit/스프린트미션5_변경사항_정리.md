## 1. 전체 개요

스프린트미션5의 핵심 목표는 **"REST API 서버로 전환"** 입니다.

기존 스프린트미션4까지는 Java 콘솔 프로그램 방식으로 동작했습니다. 즉, `DiscodeitApplication.java`의 `main()` 메서드 안에서 서비스를 직접 호출하고 결과를 콘솔에 출력하는 방식이었습니다.

스프린트미션5에서는 이 방식을 완전히 바꾸어, **Spring Boot를 활용한 REST API 서버**로 전환했습니다. 이제 외부에서 HTTP 요청(GET, POST, PATCH, DELETE)을 보내면 JSON 형식으로 응답을 받을 수 있습니다.

### 핵심 변경 요약

| 구분 | 이전 (스프린트4) | 이후 (스프린트5) |
|------|----------------|----------------|
| 실행 방식 | `main()` 안에서 직접 서비스 호출 | HTTP API 요청/응답 |
| 클라이언트 | Java 코드 (하드코딩) | Postman, 웹 브라우저, 프론트엔드 앱 |
| 에러 처리 | try-catch로 콘솔 출력 | HTTP 상태 코드 반환 (404, 400, 500) |
| API 문서 | 없음 | Swagger UI 자동 생성 |
| 프론트엔드 | 없음 | React 앱 통합 |

## 3. 기본 요구사항 구현

### 3-1. DiscodeitApplication.java 정리

**변경 전 문제점:**
```java
// 이전에는 main() 안에 200줄 이상의 테스트 코드가 있었음
public static void main(String[] args) {
    ApplicationContext context = SpringApplication.run(DiscodeitApplication.class, args);

    // 서비스 직접 호출 (스프린트4 테스트 코드)
    UserService userService = context.getBean(UserService.class);
    UserResponse user1 = userService.create(...);
    // ... 200줄의 테스트 코드 ...
}
```

**변경 후:**
```java
// 한 줄로 정리 - Spring Boot가 알아서 서버를 시작함
public static void main(String[] args) {
    SpringApplication.run(DiscodeitApplication.class, args);
}
```

**왜 바꿨나?**
- `main()` 메서드는 애플리케이션 시작 역할만 해야 합니다.
- 테스트 코드는 `src/test/` 폴더의 별도 테스트 클래스(`FunctionalTest.java`, `IntegrationServiceTest.java`)로 분리했습니다.

### 3-2. REST API 컨트롤러 추가 (controller 패키지)

> **핵심 개념**: 컨트롤러는 HTTP 요청을 받아 서비스를 호출하고, 결과를 HTTP 응답으로 반환하는 역할을 합니다.

#### AuthController.java - 로그인 API

| HTTP 메서드 | URL | 설명 |
|------------|-----|------|
| POST | `/api/auth/login` | 로그인 |

```java
// 요청 예시 (JSON 본문)
{ "username": "user1", "password": "1234" }

// 응답 예시 (성공 시 200 OK)
{ "id": "...", "username": "user1", "email": "user1@email.com", ... }

// 응답 예시 (실패 시 404 Not Found)
{ "message": "User with username user1 not found", "timestamp": "..." }
```

#### UserController.java - 사용자 API

| HTTP 메서드 | URL | 설명 | 상태 코드 |
|------------|-----|------|----------|
| POST | `/api/users` | 사용자 등록 | 201 Created |
| GET | `/api/users` | 전체 사용자 목록 조회 | 200 OK |
| PATCH | `/api/users/{userId}` | 사용자 정보 수정 | 200 OK |
| DELETE | `/api/users/{userId}` | 사용자 삭제 | 204 No Content |
| PATCH | `/api/users/{userId}/userStatus` | 온라인 상태 업데이트 | 200 OK |

**특이사항**: 사용자 등록/수정 시 프로필 이미지를 함께 업로드할 수 있습니다 (`multipart/form-data` 방식).

```java
// 내부적으로 MultipartFile → BinaryContentCreateRequest로 변환하는 헬퍼 메서드
private BinaryContentCreateRequest resolveProfile(MultipartFile profile) throws IOException {
    if (profile == null || profile.isEmpty()) {
        return null; // 프로필 없이도 가입 가능
    }
    return new BinaryContentCreateRequest(
        profile.getOriginalFilename(),
        profile.getContentType(),
        profile.getBytes()
    );
}
```

### 3-3. 전역 예외 처리 (exception 패키지)

**변경 전 문제점:**
- 예외가 발생하면 Spring Boot가 기본 에러 페이지(HTML)를 반환했습니다.
- API 클라이언트(Postman, 앱 등)는 HTML 에러 페이지를 처리하기 어렵습니다.

**변경 후:**
`GlobalExceptionHandler.java`를 추가하여 모든 예외를 **일관된 JSON 형식**으로 반환합니다.

```java
// ErrorResponse.java - 에러 응답 형식
{
    "message": "User with id {id} not found",
    "timestamp": "2026-02-19T10:30:00Z"
}
```

| 예외 타입 | HTTP 상태 코드 | 발생 상황 |
|---------|-------------|---------|
| `NoSuchElementException` | 404 Not Found | 존재하지 않는 리소스 조회 |
| `IllegalArgumentException` | 400 Bad Request | 잘못된 요청 (중복 이메일 등) |
| `Exception` (그 외 모든 예외) | 500 Internal Server Error | 예상치 못한 서버 오류 |

### 3-4. 서비스 레이어 변경

#### 반환 타입 변경 이유

이전 스프린트에서는 서비스 메서드가 `ChannelResponse`, `MessageResponse` 같은 래퍼(Wrapper) 객체를 반환했습니다. 스프린트5에서는 불필요한 래핑을 제거하고 엔티티를 직접 반환하도록 단순화했습니다.

단, 사용자 목록 조회는 **온라인 상태**(`isOnline()`) 정보를 함께 제공해야 하므로, 별도 DTO(`UserDto`)를 계속 사용합니다.

**ChannelService 변경:**
```java
// 변경 전
Channel findById(UUID id);           // 단건 조회 메서드 제거
ChannelResponse createPublic(...);   // 래퍼 객체 반환
ChannelUpdateRequest ...             // 이전 DTO 타입

// 변경 후
Channel createPublic(...);           // 엔티티 직접 반환
Channel update(UUID id, PublicChannelUpdateRequest request);  // 새 DTO 타입
List<ChannelDto> findAllByUserId(UUID userId); // ChannelDto 반환 (lastMessageAt 포함)
```

**ChannelDto가 필요한 이유:**
채널 목록에는 "마지막 메시지 시간"(`lastMessageAt`)과 "참여자 ID 목록"(`participantIds`) 정보가 필요합니다. 이 정보는 `Channel` 엔티티에 없으므로 별도 DTO로 담아 반환합니다.

```java
// BasicChannelService.java 내부의 변환 메서드
private ChannelDto toChannelDto(Channel channel) {
    // 가장 최근 메시지의 생성 시간을 계산
    Instant lastMessageAt = messageRepository.findAllByChannelId(channel.getId()).stream()
        .map(Message::getCreatedAt)
        .max(Instant::compareTo)
        .orElse(null);  // 메시지가 없으면 null

    // PRIVATE 채널만 참여자 목록을 포함
    List<UUID> participantIds = null;
    if (channel.getType() == ChannelType.PRIVATE) {
        participantIds = readStatusRepository.findAllByChannelId(channel.getId()).stream()
            .map(ReadStatus::getUserId)
            .toList();
    }

    return new ChannelDto(channel.getId(), channel.getType(), channel.getName(),
        channel.getDescription(), participantIds, lastMessageAt);
}
```

#### UserService 변경:
```java
// 변경 전
List<User> findAll();        // User 엔티티 목록 반환

// 변경 후
List<UserDto> findAllAsDto(); // 온라인 상태가 포함된 UserDto 반환
```

메서드 이름이 `findAll()` → `findAllAsDto()`로 바뀐 이유: 반환 타입이 바뀌면서 메서드 이름도 더 명확하게 표현하기 위함입니다.

### 3-6. BinaryContent 엔티티 필드 변경

```java
// 변경 전
private byte[] data;         // 필드명: data

// 변경 후
private final long size;     // 신규 추가: 파일 크기 (bytes.length)
private final byte[] bytes;  // 필드명: bytes (더 명확한 이름)
```

`size` 필드를 추가한 이유: 파일 크기를 매번 `bytes.length`로 계산하지 않아도 되고, API 응답에서 파일 크기를 바로 확인할 수 있습니다.

### 3-7. application.yaml 변경

```yaml
# 변경 전
discodeit:
  repository:
    type: jcf   # 메모리(JCF) 기반 저장소

# 변경 후
discodeit:
  repository:
    type: file  # 파일 기반 저장소 (서버 재시작 후에도 데이터 유지)

    path: /swagger-ui.html      # Swagger UI 접속 URL
```

### 4-1. Swagger UI 통합

> **Swagger란?** API 명세를 자동으로 문서화하고 웹 브라우저에서 직접 API를 테스트해볼 수 있는 도구입니다.

**SwaggerConfig.java 추가:**
```java
@Configuration
public class SwaggerConfig {
    @Bean
    public OpenAPI openAPI() {
        return new OpenAPI()
            .info(new Info()
                .title("Discodeit API 문서")
                .description("Discodeit 프로젝트의 Swagger API 문서입니다.")
                .version("v1.0.0"))
            .servers(List.of(
                new Server().url("http://localhost:8080").description("로컬 개발 서버")
            ));
    }
}
```

서버 실행 후 `http://localhost:8080/swagger-ui.html`에 접속하면 Swagger UI를 볼 수 있습니다.

**각 컨트롤러에 Swagger 어노테이션 추가:**
```java
@Tag(name = "User", description = "User API")  // 그룹 태그
@Operation(summary = "User 등록")               // API 설명
@ApiResponses({
    @ApiResponse(responseCode = "201", description = "User가 성공적으로 생성됨", ...)
    @ApiResponse(responseCode = "400", description = "이미 존재하는 이메일/username", ...)
})
```

```
    └── index-kQJbKSsj.css ← 스타일시트 (압축됨)
```

Spring Boot는 `resources/static/` 폴더의 파일을 자동으로 정적 파일로 서빙합니다. 따라서 `http://localhost:8080`에 접속하면 React 앱이 화면에 표시됩니다.

> **SPA(Single Page Application)란?** 하나의 HTML 파일로 전체 앱을 구성하고, JavaScript가 화면을 동적으로 변경하는 방식입니다.

### 4-3. FileLockProvider 추가 (파일 동시성 제어)

파일 저장소(`FileXxxRepository`)를 사용할 때 **여러 요청이 동시에 같은 파일에 접근하면 데이터가 손상**될 수 있습니다. 이를 방지하기 위해 `FileLockProvider.java`를 추가했습니다.

```java
@Component
public class FileLockProvider {
    // 파일 경로별로 Lock을 관리 (같은 경로 = 같은 Lock)
    private final Map<Path, ReentrantLock> locks = new ConcurrentHashMap<>();

    public ReentrantLock getLock(Path path) {
        // 해당 경로의 Lock이 없으면 새로 생성, 있으면 기존 것 반환
        return locks.computeIfAbsent(path, k -> new ReentrantLock());
    }
}
```

> **Lock(잠금)이란?** 한 스레드가 파일을 읽거나 쓸 때 다른 스레드가 접근하지 못하도록 잠그는 메커니즘입니다. 작업이 끝나면 잠금을 해제합니다.
