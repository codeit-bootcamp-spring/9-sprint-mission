# Discodeit Backend Project - Mission 5

## 1. 요구사항

### 기본 항목
- **RESTful API 재설계**: 기존 미션에서 구현한 API를 RESTful 원칙에 맞게 재설계하고, 제공된 API 스펙과의 정합성을 확보했습니다.
- **Postman 컨트롤러 테스트**: 설계한 API의 모든 엔드포인트에 대해 유효성 검증을 수행하고, 테스트 결과물을 Export하여 공유 가능하도록 준비했습니다.
- **Swagger API 문서화**: Springdoc-openapi를 도입하여 Swagger 기반의 인터랙티브 API 문서를 자동 생성하고 Swagger-UI를 통해 런타임 테스트를 수행했습니다.

### 심화 항목
- **정적 리소스 서빙 및 프론트엔드 통합**: 백엔드 서버에서 정적 리소스(HTML/JS/CSS)를 서빙하도록 설정하여 프론트엔드-백엔드 간의 통합 연동을 완수했습니다.
- **Railway.app 클라우드 배포**: GitHub 레포지토리와 Railway.app을 연동하여 CI/CD 환경을 구축하고, 자동 생성된 도메인을 통해 실서비스 환경에서 동작을 검증했습니다.
- **멀티파트 파일 핸들링**: `MultipartFile` 인터페이스를 활용하여 메시지 전송 시 파일 첨부 및 서버 로컬 저장 기능을 구현했습니다.
- **채널 타입별 비즈니스 로직 분리**: PUBLIC/PRIVATE 채널 성격에 따른 생성 및 조회 권한 로직을 분리하여 구현했습니다.

## 2. 주요 변경사항

- **전역 예외 처리 시스템 구축**: 각 컨트롤러에 파편화되어 있던 예외 처리 로직을 `@RestControllerAdvice`를 통해 중앙 집약적으로 관리하도록 변경했습니다. 
- **RESTful 엔드포인트 최적화**: `@RequestMapping`을 활용하여 HTTP 메서드와 경로를 명시적으로 매핑함으로써 API의 직관성을 높였습니다. 
- **이진 데이터처리 로직 고도화**: 파일 조회 API를 구현하여 특정 식별자(`binaryContentId`)를 통해 서버 내 정적 리소스에 접근할 수 있는 인터페이스를 마련했습니다.
- **DTO를 통한 데이터 캡슐화**: `UserDto`와 같은 전용 데이터 객체를 도입하여 비즈니스 엔티티가 직접 외부로 노출되는 것을 방지했습니다.
- **멀티파트 및 연관 관계 매핑**: 메시지 전송 시 JSON 명세와 `MultipartFile`을 동시에 수용하는 구조를 구축했습니다. UUID 식별자를 포인터처럼 활용하여 작성자, 채널, 메시지 간의 논리적 연결 고리를 생성하고 데이터의 무결성을 유지했습니다.

## 3. API 테스트 가이드 (Postman)
본 프로젝트의 모든 API 기능 및 테스트 시나리오는 제공된 Postman 컬렉션 파일을 통해 확인할 수 있습니다.
- **파일 위치**: `discodeit/postman/mission5.postman_collection.json`
- **테스트 시나리오**
    1. 유저 가입 및 로그인
    2. 공개 채널 생성
    3. 각 유저별 파일 첨부를 포함한 메시지 전송
    4. 채널 ID 기반의 전체 메시지 목록 조회

## 4. 멘토님께 드리는 질문
- **질문 1**: 현재 메시지 파일을 서버의 로컬 디렉토리에 직접 저장하고 있습니다. 실무에서 트래픽이 증가하여 서버 인스턴스가 여러 대로 늘어날 경우, 로컬 저장 방식이 가지는 한계와 이를 해결하기 위한 조언을 구하고 싶습니다.
- **질문 2**: 메시지 조회 시 채널 ID를 Query Parameter로 전달받아 필터링하고 있습니다. 데이터가 방대해질 경우 단순 필터링은 성능 저하가 발생할 텐데, 실무에서는 인덱스 설계나 페이징 처리를 어떤 방식으로 운영하여 성능을 최적화하는지 궁금합니다.
